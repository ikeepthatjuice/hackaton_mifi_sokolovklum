## Область

В пакете только quality/ и docs/. Общие Kotlin DTO, Gradle, CI, модели и код остальных участников не изменены. check_export.py проверяет публичную схему экспорта по заданию; это не реализация contracts и не доказательство качества распознавания.

Python 3.9+ и стандартная библиотека. Внешних Python-зависимостей нет, requirements.txt с вымышленными пакетами не нужен. Проверено на Python 3.12.14: 28 unit-тестов, checker synthetic_export PASS. measure.py фиксирует NFC/casefold и разбиение по пунктуации; ё отличается от е, числа не переводятся в слова. Сторонних пакетов нет. Это согласуемая методика, не методика организаторов.

Команды из корня пакета:

```bash
python3 -m unittest discover -s quality/tests -v
python3 quality/check_export.py quality/fixtures/synthetic_export.json --duration-ms 4000
```

Коды выхода checker: 0 — структура допустима; 1 — нарушение схемы/интервалов; 2 — ошибка чтения/JSON. Содержимое реплик и пути к данным не выводятся. Проверяются точные поля, непустой текст, speaker_N, целые миллисекунды (bool не принимается), начало/конец, порядок по start_ms, длительность при переданном параметре. Разные говорящие могут пересекаться во времени. Дубли JSON-ключей и NaN отвергаются. Формат speaker_N, отсутствие лишних полей и порядок — правила команды, их нужно подтвердить с актуальным экспортером Ярика.

Checker НЕ определяет, правильно ли распознаны слова, верны ли speaker IDs, нет ли дубликатов по смыслу и действительно ли времена указаны в миллисекундах вместо правдоподобных малых чисел. Для этого нужны аудио, эталон и ручная/метрическая проверка. Число 2 вместо 2000 само по себе невозможно отличить от легальной метки 2 мс.

## Как подготовить аудио и эталон

Согласовать формат с Яриком/Ильёй; записать собственную разрешённую речь. Скрипты ниже — вымышленные предложения для записи, НЕ эталоны существующего аудио:

- Первый: «Проверим план. Мы не переносим встречу. Начинаем в пятницу.»
- Второй: «Да. Нужно три коробки и двенадцать папок.»
- Первый: «Нет, папок четырнадцать. Я уточню завтра.»
- Третий: «Хорошо, записал.»

После записи вручную расшифровать то, что реально сказано, включая оговорки; дважды прослушать. Границы реплик разметить по аудио, не из текста сценария. Установить соответствие голосов условным ID. Для одновременной речи допускаются пересекающиеся интервалы. Попросить второго участника проверить эталон.

Аудио, реальные эталоны, гипотезы и подробные отчёты — в разрешённом локальном каталоге вне git. В репозиторий можно добавить эту методику и синтетический JSON. Не добавлять реальные данные в PR, CI artifacts и видео.

## Измерения

WER = (замены + удаления + вставки) / количество слов эталона; меньше лучше. Метод нормализации до сравнения согласовать и записать (регистр, пунктуация, числа, ё/е); нельзя менять его ради улучшения показателя. На пустом эталоне WER не делить на ноль: отдельно считать вставленные слова.

RTF = время обработки / длительность аудио. Для команды измерять от запуска обработки до готового результата с LLM, отдельно записать холодную загрузку моделей и время экспорта; финальную методику сверить с организаторами. Обязательно указать телефон/Android, commit, APK hash, версии/квантование моделей и условия. Сравнение моделей выполнять на одинаковых данных и устройстве.

Правильность голосов оценивать после сопоставления условных ID с эталоном. Пока автоматического DER нет, писать «ручная проверка назначения говорящих», а не DER. По меткам сохранять ошибки начала/конца относительно ручного эталона, не назначать неподтверждённый порог организаторов.
