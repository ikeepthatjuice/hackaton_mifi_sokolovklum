# Правило ревью команды

Применять перед каждым запросом апрува. Добавлено по прямой инструкции команды; перенос в общий AGENTS.md выполняет back отдельным согласованным изменением.

1. Проверить актуальную origin/main и `git diff --name-only origin/main...HEAD`. Не предполагать, что соседние PR уже слиты.
2. Определить владельцев. Пути модулей — относительно src/android/, остальные помечены «корень»:

| Пути | Владелец |
|---|---|
| core/*, общие *.gradle.kts, gradle/, settings.gradle.kts; корень: .github/, scripts/, models/manifest.json, AGENTS.md, .gitignore | Ярик, @lockermon4 |
| feature/import/, feature/transcript/, app/ кроме app/.../di/ | Санёк, @ikeepthatjuice |
| engine/asr/, engine/diarization/, engine/alignment/ | Илья, @gexxpel |
| engine/llm/; корень: quality/, docs/, demo/, README.md | Сюбик, @bondarjuice |

3. Основной reviewer: front/ml → Ярик; back → Санёк или Сюбик; LLM-код Сюбика → Илья; docs Сюбика → Санёк. Дополнительно нужен владелец каждого чужого пути и каждый затронутый потребитель изменяемого API (pipeline, экспорт, PCM, DTO). Для core/contracts нужны все потребители: Санёк, Илья, Сюбик. Модульные native/Gradle настройки LLM дополнительно проверяет Ярик до подключения в общую сборку.
4. Перед запросом проверить CI и Draft. При красном CI или Draft апрув не запрашивать. Если CI не запускался, указывать это явно, не называть локальные тесты зелёным CI.
5. Назначить необходимых reviewers в PR и подготовить по одному сообщению каждому:

```text
[Имя], нужен апрув PR #N — <название>
Ссылка: <url>
Тебя касается: <пути/API и изменение>
Проверь: <2–3 конкретных пункта>
CI: <зелёный/красный/не запускался>
Блокирует: <что ждёт этот merge>
```

6. Свой PR не апрувить и не мерджить. Новые коммиты требуют повторной проверки, сброса устаревшего approval и нового запроса. Не отправлять личные сообщения автоматически без прямого поручения.
